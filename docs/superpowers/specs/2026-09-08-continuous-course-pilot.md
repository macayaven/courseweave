# Continuous course pilot: accepted implementation scope

The user accepted discovery phases 0–3 and authorized implementation through a polished first testing session. The initial tester was the local pilot owner; the first course is `macayaven/agent-harness-path`, branch `feature/courseweave-integration`. This specification supersedes incompatible unpublished-v1 assumptions in the divergent September 4 design. It records the accepted conversation, rather than introducing another approval gate.

## Product promise

CourseWeave accompanies a technical learner through an authored course, adapting explanations and optional practice to observed needs. It also helps the technical expert author reduce administrative work through reviewable curriculum drafts. It does not replace the course, its assessments, or its certification authority. Commercial SaaS is a hypothesis to test after this local pilot; there is no tenancy, billing, or hosted execution in this delivery.

Each pilot session preserves the course's sequence: a 20–40 minute lesson with substantial theory, a diagram, and dated sourced state-of-the-art material; a 30–60 minute notebook containing a complete toy system from a real domain with predictions and attempts before solutions; native foldable self-checks; and optional hard-path labs using recorded replay or explicitly requested live execution. S01 and S02 receive the full guided experience. The remaining course content remains accessible and honestly labeled as not yet given the pilot's structured guidance.

There is ONE persistent Course assistant in one rail and one conversation. Moving from reader to notebook, self-check, or lab updates context and available help without changing assistant identity, creating separate chats, or moving the composer. The rail is useful immediately, concise, keyboard usable, responsive to a narrow viewport, and includes both learner and assistant turns. Turn context is immutable while a response streams; the next turn uses newly confirmed activity context. Session-only conversation survives ordinary hide/show and navigation but is never stored as durable raw chat.

## Authority and contracts

Use schema version 2 for the incompatible course format. Reuse the closed contracts in the divergent worktree where sound, but the release must have one active manifest authority across Python, schemas, APIs, Learn, Author, and Lab. Schema 1 is accepted only by an explicit copy-producing migration path with a mapping report; normal launch/save reject it with actionable guidance. Empty structurally valid Author drafts are supported; runnable validation is stricter.

Experience controls presentation only. Required, optional, and excluded progress are distinct. Completion is the conjunction of declared requirements, evaluated from valid directly submitted records or ordinary present artifact files. Opening a page, running a cell, revealing a solution, a model assertion, or an arbitrary completion flag cannot confer completion or certification. Text, evidence, and attestation remain explicitly labeled learner submissions; a file's presence is not correctness. Teacher access, gates, hints, sharing, and proposals come from explicit policy, independently of experience. Disabled and observer-only access never invokes a provider.

Learner state lives outside course source under a platform-appropriate personal directory keyed by canonical course identity/root. Records are bound to valid manifest coordinates and requirement digests; cosmetic edits retain them, substantive requirement changes make old records non-counting, and removed records remain inspectable orphans. State revisions, exact manifest ETags, idempotency, locking, and crash recovery retain their established guarantees. Old state import is explicit, copy-only, and reports unmappable items. Provide state export/reset controls with no raw conversation or secrets in exports.

Learning objectives, authored guidance and progressive hints, duration, and simple deterministic formative questions are optional closed course metadata. Formative correctness is separate from submitted completion facts and certification. Persistent adaptation requires visible opt-in, inspectable evidence/preferences, revocation, and reset. Suggestions name their evidence and remain optional. No inferred personality traits, automated certification, or AI-authored progress.

## Grounded teaching and providers

Each turn receives a bounded context of course/activity titles, authored objectives/guidance, requirement status, explicitly selected relevant learner evidence, preferences/time budget, and consent. Course lesson text requires a clear bounded learner action to use that lesson under explicit-only content sharing. Workspace selections, cells, and outputs retain one-run explicit Share scope and their existing ephemeral handling. Never silently send solution cells, outputs, credentials, or arbitrary open files. The assistant can explain an authored concept and suggest an approved revisit without inventing course content or changing the path.

Keep the REST service the only durable mutation authority, AG-UI inert, provider keys in runtime custody, terminal execution learner-only, and course sources authoritative. Remove unused learner workspace/phase-record proposals from active tools; retain reviewable Author course drafts and explicit preference workflows. Maintain server-side conversation identity independently of the navigation source, and rebuild policy on every run. A successful text answer must leave a truthful Ready status; interruption and retry must preserve attribution and avoid duplicate turns.

Provider support is capability-based: text-only is a complete fallback, streaming/tool/structured-result behavior is explicitly declared and tested rather than inferred from an OpenAI-compatible URL. Bound timeouts/context and distinguish auth, rate limit, refusal, truncation, cancellation, and connectivity failures without leaking credentials or mutating state. Version prompts and evaluation fixtures. Test at least two heterogeneous provider behavior profiles; make a bounded real configured endpoint canary when runtime custody makes it available. Report clearly if live endpoint evidence is unavailable, rather than claiming interoperability. Reasoning traces and multimodality are not necessary for this pilot.

## Delivery and evidence

Work from the latest verified v0 baseline in an isolated platform worktree and a separate course integration worktree. Preserve the protected dirty companion and divergent fix1 worktree. Keep course source, notebook cell IDs/outputs, licenses, and native verification intact except reviewed pilot metadata and generated reader assets. Sandboxed reader diagrams must be rendered statically; never enable arbitrary scripts to make Mermaid work. Replay remains distinguishable from live and requires no credentials.

Deliver an installed artifact and a one-command local pilot launcher with the course kernel isolated from the platform environment. Preserve artifact determinism, exact installed-wheel tests, shutdown credential scans, CAS/sharing regressions, Author interaction coverage, and the course's native verification. Perform a real browser pass covering entry, S01/S02 navigation, continuity, progressive help, deterministic records/checks, no-provider behavior, reviewable Author edits, narrow/keyboard usability, and explicit replay/live affordances. Record evidence and exact startup instructions with a short first-test route.

Phase 3A is a personal exploratory test, not proof of learning efficacy or market demand. Include a small independent transfer assessment and a test protocol comparing ordinary/static help with optional adapted help, with delayed checks and predeclared exploratory criteria for later participants. Do not manufacture user outcomes. No push, merge, publication, or SaaS rollout is required for this handoff.
