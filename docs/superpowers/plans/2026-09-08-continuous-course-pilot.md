# Continuous course pilot implementation plan

**Goal:** Deliver the accepted continuous-assistant S01/S02 course pilot ready for the initial tester to use locally.
**Spec:** `docs/superpowers/specs/2026-09-08-continuous-course-pilot.md`
**Architecture:** Preserve FastAPI/PydanticAI/SQLite and React/JupyterLab; canonical closed v2 manifest; pure deterministic learning engine; external personal state; one contextual assistant.
**Base:** platform `07c882e5348c5dbe43b3c77db7d5523113111992`; course integration `7e849558de4d19ffdf4f245c3a9045b96361bb78`.

## Global Constraints

- Work only in the isolated CourseWeave pilot worktree and, for the adapter task, the isolated Agent Harness Path integration checkout. Never modify the protected companion, original checkouts, or divergent fix1 worktree. No push, merge, publication, global config edits, or secret disclosure.
- One persistent Course assistant and session conversation spans reading, notebooks, self-checks, and optional labs. Experience never grants authority. Explicit course policy and valid direct learner records determine gates. No AI completion or certification.
- One active schema version 2 at delivery. Schema 1 survives only in explicit migration tooling. Preserve CAS, idempotency, transactional recovery, explicit ephemeral sharing, learner-only terminal execution, and session-only raw chat.
- Preserve existing meaningful regression coverage. Add focused failing tests before behavior changes; run targeted checks while iterating and relevant full suites once before task completion. Do not delete assertions merely to make a new format pass.
- Never dispatch subagents from an implementation or review task. The controller owns serial implementation dispatches, task review, and final review. Local commits in owned pilot branches are authorized. Write detailed reports to the provided scratch path and return concise status.
- Tasks are integration checkpoints, not independent release candidates. Tasks 1–5 may stage a cutover, but every active runtime/client and test fixture must use v2 before final packaging. Do not introduce a lossy v2-to-v1 runtime adapter.

## Task 1: Canonical v2 contracts, migration, and pure engine

**Own:** new `src/courseweave/contracts/`, `src/courseweave/engine/`, `src/courseweave/migration/`, focused contract/engine/migration tests and normative v2 schema. Read the closed contracts and tests in the divergent earlier CourseWeave fix worktree as reusable source; do not cherry-pick its divergent runtime or weaken the newer baseline. Keep normal runtime cutover for Task 2, with the new schema staged under contracts until then.

**Produce:** canonical `CourseManifest` and semantic/path validation APIs; JSON schema generated from that authority; explicit pure legacy conversion returning manifest and mapping report; requirement/curriculum digests, validated record/value contracts, progress evaluator, and effective teacher policy helpers consumed by Tasks 2–5.

1. Adopt closed discriminated models using literal version 2. Retain independent experience/progress/teacher and typed surfaces/requirements. Allow `modules=[]` with `entry_module_id=null` for drafts; runnable validation requires meaningful entry content. Validate local paths/HTTPS URLs, IDs/references, selector semantics, symlink escapes, policy bounds, and notebook/runtime relationship. Prefer existing baseline path protections where already stronger.
2. Add a small closed optional `learning` object per phase: objective IDs/text; duration min/max minutes; authored overview; progressive hints; source references with labels, HTTPS URLs and optional reviewed date; deterministic single-choice checks with stable option IDs, correct answer and explanatory feedback. Bound collection/text sizes and validate objective/option references. These are teaching metadata, not completion authority. Do not add executable grading or generic plugin registries.
3. Provide a closed coordinate `(module_id, phase_id, requirement_id)` and record values for text, evidence, and attestation. Keep stored kind/origin/digests server-owned. Derive completion using AND across matching records, with optional/excluded phases outside the required denominator. Define an empty requirements list explicitly as no task-specific submission required (runnable validation must prevent empty courses masquerading as progress). Artifacts reject symlinks, inspect ordinary-file presence without contents, and can become incomplete after deletion. Stale or orphan records never count.
4. Requirement digests cover substantive requirement content and coordinates, not cosmetic phase/module titles or teaching presentation. Curriculum digest covers learning/progress/policy structure consistently and is separate from exact-byte ETag. Effective teacher policy is independent of experience and checks only currently valid same-phase records; observer/disabled are never provider-callable.
5. Explicit legacy conversion preserves IDs/content paths and reports every semantic mapping. Ambiguous mixed notebook selectors and unsupported video ranges are surfaced rather than silently truncated. Normal runtime must not call this converter; expose CLI in Task 2. Use a retained isolated legacy reader rather than importing active old models after cutover.
6. Tests: closed schemas reject legacy-v1/extra keys/coercion; generated-schema parity; valid empty Author draft vs invalid runnable; paths and selectors; policy cannot be escalated by display; stale/fabricated records don't complete; optional/excluded denominator; artifact disappearance/symlinks; migration previews don't modify inputs. Run focused tests and baseline Python suite (runtime remains old in this checkpoint). Commit and report public interfaces precisely for Task 2.

Bind persisted state to course identity and separately version its schema. Never silently consume in-course old SQLite. 3. Direct `put_record`/`clear_record` REST actions carry coordinates, closed value, expected state revision, and curriculum digest. Remove arbitrary `complete_phase` and model `phase_record` mutation; return derived progress, stale/orphan status, and effective teacher availability in bootstrap/state responses.
4. Add opt-in learning adaptation preferences, simple time budget, structured deterministic check attempts bound to objective/check revision, and inspect/export/reset/delete paths. Deterministic formative feedback is separate from completion. No raw chat in durable state. Preserve prior durable records without treating them as verified mastery.
5. Keep API/proposal enforcement consistent with explicit policy; remove active learner workspace proposal tools, retain reviewable Author manifest drafts. Introduce minimal canonical transport types that frontend tasks can consume directly. Existing professor may need mechanical updates for v2 here; substantive grounded teaching is Task 3.
6. Tests: arbitrary/stale coordinate/digest/kind/origin rejection, cosmetic retention/substantive invalidation, concurrent state edits, replay under later revision, external path/source cleanliness, import no mutation, removed artifact re-evaluation, policy independent of display, check-answer validation, consent/export/reset without chat/secrets. Preserve/run full Python suite. Commit; report endpoint shapes, TypeScript payload examples and migration command for downstream tasks.

## Task 3: Continuous grounded teaching and capability evidence

**Own:** `professor.py`, `providers.py`, assistant portions of `api.py`, bounded grounding/evaluation helpers, Python provider/pedagogy/stream tests and fixtures. Consume canonical policies, external state, objective/check facts and consent from Tasks 1–2.

1. One server-bound conversation identity per authenticated session/role/thread independent of navigation source. Snapshot activity/policy for each accepted run; new turns use current context and old turns retain attribution. Existing bounded session history and explicit one-run Share lifetime remain. Client history never becomes trusted authority.
2. Construct versioned, bounded course/learner context from authored metadata, valid submitted records, check facts, time budget/preferences only under appropriate consent. Offer optional adaptations with evidence explanation and approved revisit targets; learner can decline. Do not infer personality or award mastery. Treat authored/user text as data, avoid solution leakage before prediction/attempt gates, and distinguish observations from assessments and guesses.
3. Add explicit bounded course lesson grounding action with server-resolved approved surface, safe extraction and source labels; do not read arbitrary paths or auto-share notebook answers/output. Lesson grounding and current-run workspace Share have visible scopes and clear reset behavior. Hint requests stay in the same conversation.
4. Implement tested provider capability configuration for text, streaming and tool/structured support; text-only fallback is useful and cannot receive unusable tools. Bound input/timeouts; classify refusal/truncation/auth/429/cancel safely. Provider URLs cannot come from course files. Do not store keys or reasoning traces. Keep provider usage/config fingerprints free of secrets.
5. Add reproducible versioned evaluation scenarios: grounding/citations; wrong answer targeted explanation; progressive hint; no answer before attempt; voluntary revisit; opt-out prevents cross-session evidence use; navigation changes authority without splitting history; invalid/refused/truncated tool data has no mutation. Exercise two heterogeneous behavior profiles and deterministic no-provider behavior. Real endpoint canary and empirical results are completed by Task 7 when local custody is available; do not fake evidence.
6. Run focused regression and full Python suite; commit. Report frontend events/actions/statuses, required config fields and evaluation commands/results.
